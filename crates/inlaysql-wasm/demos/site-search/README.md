# Static-site search (`demo/site-search`)

The first of the `demos/`: full-text **and** vector search for a website that
has no backend at all — the deployment shape a government or compliance-bound
static site needs, where adding a search API is exactly the thing you cannot
do.

**Live: <https://inlaysql.github.io/inlaysql/demo/site-search/>** (published
from `main` by [`wasm.yml`](../../../.github/workflows/wasm.yml), same
deployment as the [main demo](https://inlaysql.github.io/inlaysql/)).

## The shape

```
pages.json ──cargo run --example site_search_fixture──▶ site.inlay
                                                            │
your HTML ──────────────────── deploy ────────────▶ visitor's browser
                                                    opens it with the
                                                    WASM module, runs SQL
```

The index is **built once, at deploy time, natively** — where you have the
site's pages and as much time as you like — and shipped as a static asset
beside the HTML. The visitor's browser fetches `site.inlay` like an image,
opens it with the ~660 KiB WASM module, and every search runs in that tab. No
search API exists to attack, log, rate-limit or take down.

## What each file is

| File | Role |
| --- | --- |
| `pages.json` | The corpus: `dim` plus one entry per page (`path`, `title`, `body`). Stands in for a sitemap, a crawl, or your build system's page list. |
| `index.html` | The page itself. Loads the WASM module from `../../pkg/` (the same module the main demo loads — no copy, no version skew) and runs one SQL statement per search. |
| `site.inlay` | Generated by the fixture, git-ignored like all `*.inlay`. Never edit by hand. |

The fixture lives outside this directory, with the other examples:
`crates/inlaysql-wasm/examples/site_search_fixture.rs`.

## Run it locally

```sh
./crates/inlaysql-wasm/build.sh --serve
# then open http://localhost:8000/demo/site-search/
```

`build.sh` copies this directory and the built `site.inlay` into
`www/demo/site-search/`, which is what Pages publishes — the demo at the URL
above is exactly these files.

## Adapting it to a real site

1. **Pages** — replace `pages.json` with your pages. `body` is what BM25
   ranks; keep in it the text a reader should be found by, not navigation
   boilerplate.
2. **Dimension** — set `dim` to your embedding model's output width. The demo
   page reads the width from the shipped schema rather than hard-coding it, so
   this is a corpus change, not a page change.
3. **Embeddings** — the fixture uses `hashed_embedding`, the engine's stand-in
   (it matches strings that *spell* alike, not meanings). A real deployment
   computes its own model's vectors for every page at build time and inserts
   those instead; the page needs no change, because it embeds only the *query*,
   with whatever function you swap into `statementFor`'s `semantic` and
   `hybrid` arms. Whatever produces the stored vectors must also produce the
   query vectors — mixing models silently degrades ranking, which is the kind
   of bug nobody files.
4. **Rebuild and deploy** — rerun the fixture and ship the new `site.inlay`
   with the rest of the site. Content changed? That is the whole update:
   re-index, re-upload.

## What this demo does not claim

- **No sync.** The database is a static asset; updates are a rebuild and
  re-upload, which for a static site is the normal publishing step anyway.
- **The embedder is a stand-in.** Point 3 above is the one real decision a
  deployment makes.
- **Corpus size.** The demo ships 16 pages. A few thousand pages with
  `VECTOR(384)` is a few MB compressed — fine as an asset, but measure with
  your own corpus before promising anything.
